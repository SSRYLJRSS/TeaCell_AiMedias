# 性能手册

> 更新日期：2026-09-13
>
> 修改图像、视频、列表、搜索、同步或并发代码前必须阅读本文。

## 1. 目标与基线

| 场景 | 目标或已观测基线 |
|---|---|
| JPG 320px 缩略图 | 目标 ≤5ms；历史 dev 实测约 1.9ms |
| RW2 320px | 目标 ≤100ms；历史实测约 57ms |
| RW2 1280px 高清 | 历史实测约 81ms |
| dev 全图解码 | O3 后历史实测约 0.37s，对比未优化 12.7s |
| 3 万素材网格 | 滚动无明显白块、卡顿或持续内存增长 |
| 搜索响应 | 产品目标 ≤500ms，体验目标 <300ms |
| 入库 100 图 | 立即出现占位图，主界面不冻结 |
| 打标批次 | 进度持续，网络任务不阻塞 UI |

性能数字依赖机器、样本和构建配置。记录结果时必须写明：

- 构建类型：dev/release。
- CPU、GPU、磁盘和系统。
- 文件格式、尺寸、压缩和数量。
- 是否命中缓存。
- 测试命令和原始输出。

## 2. 图像解码

### 2.1 策略

通用解码只经 `services/imaging.rs`：

1. 尺寸探测和轻量元数据。
2. EXIF/TIFF/CR3 等内嵌预览提取。
3. JPG 不做会把主图抓回的标记扫描。
4. 占位层不做昂贵 RAW 全解码。
5. 高清层才进入 HEIC/RAW 专用解码下游。
6. 全局许可限制并发。

### 2.2 内嵌预览

相机 RAW/JPG 通常包含可快速提取的预览。关键约束：

- TIFF IFD 偏移相对 TIFF 基准，不是文件头。
- RW2 魔数为 `0x55`，Panasonic 预览可能位于 `0x2E`。
- JPEG 裁剪要容忍首尾填充字节。
- `.jpg` 禁止 FFD8 标记扫描兜底。
- 提取失败才进入兼容降级。

### 2.3 二维分箱

RAW 真解码使用 2×2 Bayer binning 生成预览级图，避免完整去马赛克的高成本。它面向缩略图，不承诺专业级显影。

### 2.4 开发构建优化

图像、RAW、颜色处理相关依赖必须在 `src-tauri/Cargo.toml` 的 dev profile 中使用合理优化级别。新增相关 crate 时同步检查：

```toml
[profile.dev.package.<crate>]
opt-level = 3
```

### 2.5 并发和锁

- 解码使用有界并发，禁止无限线程。
- DB 锁内只做短查询和写入。
- 解码、网络和大文件 IO 必须在锁外。
- 高清缩略图生成需要缓存命中和二次检查。

## 3. 视频

- 首页/网格优先使用封面或轻量预览。
- 悬浮播放必须有单实例、延迟触发和滚动抑制。
- 不兼容格式按需生成代理，不预转码整个库。
- 代理任务必须有状态、取消、清理和缓存统计。
- 视频 AI 抽帧限制帧数和分辨率，视频结果需要多帧证据合并。

## 4. 前端

| 场景 | 策略 |
|---|---|
| 素材网格 | TanStack Virtual 虚拟滚动 |
| 缩略图 | 占位图优先，高清图按需替换 |
| 入库清单 | 小列表模式不渲染重型缩略图 |
| 预览 API | 模块级缓存，重复路径不重复调用 |
| 搜索 | 输入防抖，旧响应不得覆盖新请求 |
| 查看器 | 高清/原图分层，缩放平移只改 transform |
| 任务进度 | store 聚合事件，避免页面重建全部列表 |

## 5. 搜索

- 普通搜索使用 FTS5/参数化谓词，不拉回全部 ID 再拼长 IN。
- 超级搜索列表、总数、全选和诊断共享 SearchPlanV3。
- 排序必须有稳定尾缀，避免分页重复或跳过。
- 诊断不能在每次输入时无限并发；需要 revision 丢弃旧响应。
- 大结果集的全选上限必须有明确截断和 UI 提示。
- 修改索引、SQL 或排序后必须用 3 万级数据验证。

## 6. 色彩和元数据回填

- 色板、感知哈希和媒体元数据回填必须分批、可取消、可观测。
- 批处理不得长期持数据库锁。
- 回填只更新目标字段，避免触发无关列表全量刷新。
- 大图提色应使用缩略图或采样，不读取原图全像素。

## 8. 常见反模式

1. 在数据库锁内解码、请求网络或读取大文件。
2. 引入第二套图片解码路径。
3. 把全量结果或大对象写进 React state。
4. 每次 hover 都创建播放器或并发请求原图。
5. 用未优化的 debug 配置判断库性能。
6. 为消除分页问题而无限增大 limit。
7. 在输入防抖链路中允许旧响应覆盖新响应。
8. 为了“实时”重复扫描整个媒体库。

## 9. 2.0 Agent Windows工程预算（已独立复核）

2026-10-09，用户授权的独立复核者 `/root/review_agent_runtime` 批准以下 Windows x64 工程预算及检查条件。该批准固定后续实现的上限，不代表当前最终制品、所有A0任务或发布已通过；实际状态和原始测量证据只见[PROJECT_PLAN第9节](PROJECT_PLAN.md#9-20-agent开发状态)。目标平台支持等级沿用[PLATFORM](PLATFORM.md)，Mac/Linux须分别建立本机基线并取得复核，不沿用Windows验收结果。

| 项目 | 批准上限 | 检查条件及理由 |
|---|---|---|
| Windows x64 NSIS增量 | 增量≤50MiB，且“安装包增量÷无Agent基线包体”≤160%，两项均满足 | 用同配置实际安装包字节数和 SHA-256 核算；百分比明确以无Agent基线包体为分母。依据原型制品测量保留实现余量，仍要求处理不必要资产；A3/A6按最终配置重测 |
| Agent附加运行时解包总量 | ≤250MiB | 单目标实际随包文件总量，含Node/Pi/原生模块/许可；不把压缩包大小当解包大小，不把源node_modules总量当最终安装量 |
| Windows Host新进程SDK ready | 每次≤5秒 | 固定随包Node、无系统Node、无真实模型，至少10次独立进程并保留原始样本；不含模型首token，不能称磁盘冷缓存测量 |
| 正常退出 | 每次≤1秒 | 仅空闲或已停止推理的Host正常退出；业务任务中断另验证状态/收据，不以强杀满足正常退出指标 |
| Node Host空闲working set | ≤192MiB | SDK初始化后、单Host、无模型请求；实际部署需扣除测量器/fixture，同条件重复采样 |
| Node Host单流working set与进程峰值 | ≤256MiB | 短文本、340KB Unicode、1.8MB文本请求各至少10次；数据含请求构造/上传与结果消费；多会话切换及压缩另回归 |
| 独立Rust网关增量working set | ≤32MiB | 仅适用于当前debug独立原型比较；生产网关进入主Rust进程后须重新定义相同基线的主进程增量，不能直接复用进程总量 |

这些上限是已批准的Windows工程门禁，不是硬内存沙箱或收费限额。当前网关每个profile已有10次连续请求、生命周期有10次新进程样本，准确结果见项目计划；它们没有干净机器、磁盘冷缓存、最终GUI或其他平台证明。网关样本共用一个Node进程，fixture/采样器仍影响负载；安装包实测对应较早的资源overlay，也没有冒充当前完整代码包。新代码、大批量媒体与生产GUI可能增加资源，须在A3/A6按最终制品重测。

独立复核已确认以下工程代价：完整Pi/Node会增加安装体积和常驻内存；保持一个宿主并按需启动，不能通过移除授权/恢复能力来压预算。若后续任一指标超限，先定位重复依赖、未用原生资产与上下文投影，不静默调整阈值；更改由同一架构/发布复核角色明确批准。其他平台在其本机建立相应基线，Windows数字不作为已获批准的Mac/Linux预算。
