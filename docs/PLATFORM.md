# 平台支持与差异治理

> 更新日期：2026-09-23
>
> 本文档是支持平台、支持等级、平台能力差异和跨平台开发边界的唯一事实源。产品功能见
> [PRD.md](PRD.md)，当前落地状态见 [PROJECT_PLAN.md](PROJECT_PLAN.md)，验证方法见
> [TEST_STRATEGY.md](TEST_STRATEGY.md) 和 [QA_PLAYBOOK.md](QA_PLAYBOOK.md)。

## 1. 支持目标

当前阶段面向少量知情测试者验证统一代码主线，不承诺三个平台具有相同的功能完备度。

| 平台 | 首发目标 | 支持等级 | 核心承诺 |
|---|---|---|---|
| Windows | Windows 10/11 x64 | 正式支持目标 | 完整功能、完整自动化门禁和真机 UAT |
| macOS | Apple Silicon | 预览支持目标 | 可安装、可启动，核心五步闭环通过真机验收 |
| Linux | Ubuntu 24.04 LTS x64 | 预览支持目标 | 可安装、可启动，核心五步闭环通过真机验收 |

首发范围不包含 Intel Mac、其他 Linux 发行版和其他 CPU 架构。扩大范围必须先增加对应构建、
测试和真机证据，不能只修改宣传文案。此表定义目标，不表示验收已完成；当前证据只记录在
[PROJECT_PLAN.md](PROJECT_PLAN.md)。

## 2. 支持等级

| 等级 | 证据要求 | 对外表述 |
|---|---|---|
| 正式支持 | 自动化门禁、完整 UAT、安装与回滚路径均已验证 | 可供目标用户日常使用 |
| 预览支持 | 自动化门禁通过，且当前版本核心五步闭环已在目标真机验证 | 核心流程可用，允许公开已知的次要问题 |
| 实验构建 | 自动化构建通过，但当前版本尚无完整真机证据 | 仅供知情测试者试用，不宣称已支持 |
| 不支持 | 未进入支持范围，或能力被产品决策明确排除 | 入口禁用或不展示，并说明原因 |

核心五步闭环固定为：**导入 → 浏览 → 搜索 → 查看 → 导出**。任一步无法完成，该平台当前版本
不能标记为预览或正式支持。

## 3. 统一主线与发布原则

1. 只维护一个长期 `main`，功能分支按行为目标划分，不建立长期平台分支。
2. 同一版本的三端安装包必须来自同一个 Git 标签和提交；公开时间可以不同。
3. 候选阶段发现任一平台核心闭环失败时，修复并生成新的候选；最终标签前必须满足各自等级。
4. 日常 macOS/Linux 编译或测试失败会阻止合并。基础设施故障只能临时豁免，必须记录原因、
   责任人、恢复条件和期限；不允许永久 `continue-on-error`。
5. 第一阶段不承诺把某一操作系统的数据库和素材目录直接搬到另一系统继续使用。数据库 schema
   和业务语义保持一致，但跨系统搬库属于独立产品能力。

## 4. 功能能力矩阵

| 能力 | Windows | macOS | Ubuntu | 产品处理 |
|---|---|---|---|---|
| 导入、浏览、搜索、查看、导出 | 完整 | 核心闭环 | 核心闭环 | 三端使用同一业务语义 |
| 云端或用户自建兼容 AI 服务 | 支持 | 支持 | 支持 | 走统一外部连接协议 |
| 应用托管的默认 Ollama | 支持目标 | 不支持 | 不支持 | 非 Windows 禁用托管入口，引导配置外部兼容服务 |
| 系统凭据存储 | Windows 原生后端 | Apple 原生后端 | Secret Service | 不可用与未配置必须区分 |
| HEIC、RAW、视频与外部媒体工具 | 以真实构建和样本为准 | 以真实构建和样本为准 | 以真实构建和样本为准 | 不根据操作系统名称猜测运行时可用性 |
| 跨系统素材库搬迁 | 不承诺 | 不承诺 | 不承诺 | 后续单独设计迁移协议 |

能力矩阵描述产品承诺，不代表代码已经全部完成。当前证据和缺口只记录在
[PROJECT_PLAN.md](PROJECT_PLAN.md)，避免把阶段进度混入长期契约。

## 5. 平台差异的放置规则

开发前先按接触对象分类：

1. **数据与业务逻辑**：SQL、状态机、搜索、标签和通用 UI 默认三端一致，不引入平台假设。
2. **操作系统资源**：路径、文件名编码、进程、权限、凭据、窗口、快捷键和外部二进制必须显式
   设计平台分派和测试。
3. **平台专属能力**：允许能力不同，但必须由后端统一能力入口声明；前端消费能力，不自行探测
   `navigator.platform` 或散落 `isWindows` 判断。

静态能力、运行时健康和产品开关是三种不同事实：

- 静态能力由编译目标决定，例如是否允许应用托管 Ollama。
- 运行时健康由所属服务探测，例如 keyring、FFmpeg 或解码器是否实际可用。
- 产品开关由设置或发布策略决定，不能伪装成平台能力。

当前静态能力 DTO 还声明视频兼容代理的首选变体：Windows/macOS 为 `h264_mp4`，Ubuntu 为
`vp8_webm`。省略变体时由后端按编译目标选择；前端只消费 `platformStore`，不能在组件中自行猜测。
非 Windows 的 Ollama 管理命令在任何文件、网络或进程操作前返回 `unsupported`，但外部兼容 AI
服务的连接与健康探测仍可使用。

打包版 FFmpeg/FFprobe 作为 Tauri sidecar 随安装包提供。发布构建只解析主程序同目录且通过版本
探测的 sidecar；sidecar 缺失、不可执行或探测失败时必须失败关闭，**不得**调用系统 `PATH` 的同名程序。
只有开发构建才允许在 sidecar 缺失或不可用时回退到系统 `PATH`。目标文件名、固定来源、SHA256 和所需编码器由
`src-tauri/binaries/manifest.json` 管理；`scripts/desktop.mjs` 的严格检查必须先通过，才允许打包。
manifest 中的许可证文本只用于随包告知；公开分发还必须提供对应源码和构建材料，具体门禁见
[发布流程](OPERATIONS.md#52-三端候选构建)。媒体工具从固定源码自建，不自动链接 runner 上的第三方媒体库。

HEIF/HEIC 使用 `heif-rs` 与目标专属静态库。`src-tauri/native/heif-manifest.json` 固定三端归档
SHA256、ABI 目标、头文件版本、上游源码提交和 LGPL/GPL 许可证文本摘要，并固定每个目标提取后
静态库的 SHA256；准备脚本校验后缓存到被 Git 忽略的目录，v2 验证标记还记录逐库摘要。`build.rs` 每次构建都会
复算静态库和许可证摘要，并与版本控制中的固定摘要逐一比对，拒绝缺失、被改写或目标不符的缓存，防止复用已污染的本机缓存或 Cargo
静默联网下载错误 ABI。旧 v1 缓存只有在与重新下载并验证过的固定归档逐库一致时才会升级；否则保留
旧缓存并失败，不覆盖本机数据。
组合安装包适用 GPL-3.0-or-later。HEIF 的三个静态库源码和构建脚本必须进入对应源码包，不能用
来源链接或许可证文本代替。依赖自身的许可证和原版权声明继续保留。

Rust 目标依赖放在 `Cargo.toml` 的 `[target.'cfg(...)'.dependencies]`。平台条件分支应收敛到
能力层或所属 OS 服务边界；新增散落的 `cfg(target_os)` 必须在评审中说明为何不能收敛。

## 6. 高风险区域

后台探针、媒体工具与托管服务统一经 `utils/process.rs` 启动；Windows 创建子进程时设置 `CREATE_NO_WINDOW`，不能以重定向输出或主程序 GUI subsystem 代替。非 Windows 不设置 Windows 进程标志。用户主动安装时的权限/安装器界面与后台控制台分别验收；GUI 安装器还须保留静默参数。
托管安装包缓存只在 `managedOllama` 已就绪且允许时读取；未知/失败能力状态和非 Windows 不发托管请求，通用缓存统计仍可使用。

碰到以下领域时，必须阅读本文并增加目标平台测试：

- 路径分隔符、大小写和非 UTF-8 文件名。
- 系统凭据、文件权限、文件锁和 SQLite WAL。
- 外部进程、sidecar、安装器、PATH 和可执行文件权限。
- HEIC/RAW/视频解码器及其原生依赖。
- 窗口装饰、快捷键、系统托盘和文件选择器。
- 打包格式、代码签名、公证和 Linux 系统库。

路径必须区分原生可打开路径、比较/索引键和可移植迁移路径，不能用一种字符串规范化同时承担
三种职责。首发应用和数据库 IPC 使用 UTF-8 路径；无法无损表示的导入文件必须在扫描阶段跳过并
明确告警，原文件保持不动。来自操作系统的 `OsString`/`PathBuf` 应尽可能保留原生形式直到文件或
进程调用；穿过 JSON/SQLite 字符串边界时用可失败转换，不能用 `to_string_lossy()` 生成后再拿去打开、
删除或启动进程。仅用于日志/显示的有损文本不得回流成操作路径。

## 7. 验证与缺陷口径

- 数据损坏、误删、数据库不一致在任何平台都是 P0。
- 无法安装、启动或完成核心五步闭环会阻止该平台发布。
- Windows 正式支持功能失效按正式版严重度处理。
- macOS/Linux 次要问题可以作为已知问题随预览版本发布。
- 已明确标记为不支持的平台能力不算缺陷；错误暴露入口、假成功或静默降级仍算缺陷。

自动化 CI 只能证明编译和自动测试下限，不能替代桌面真机验收。测试者反馈至少包含应用版本、
Git 提交、操作系统与架构、失败步骤、预期与实际、素材包版本以及脱敏日志或诊断包。

## 8. 安装包范围

第一阶段目标产物：

- Windows：仓库当前采用的 Tauri 安装包格式。
- macOS Apple Silicon：DMG。
- Ubuntu 24.04 x64：AppImage 和 DEB。

未签名的 macOS 包只能标记为实验构建并交给知情测试者。进入更正式的预览分发前，应完成签名
与公证方案。构建、签名和发布操作见 [OPERATIONS.md](OPERATIONS.md)。
