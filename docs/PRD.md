## 1. 产品定义

### 1.1 一句话定位

产品名称为“茶馆AI素材管理”，英文全名为“TeaCell AI Media Manager”，界面短名为“茶馆”。安装包产品身份和新安装默认目录使用英文全名，中文界面短名与安装器中文语言支持保留。升级与数据目录兼容规则见 [OPERATIONS.md](OPERATIONS.md)。为个人创作者提供一个本地优先、批量高效、可解释的图片/视频素材库，让素材“进得来、找得到、打得快、拿得走”。

### 1.2 目标用户

- 摄影师、设计师和自媒体创作者。
- 主要管理数千到数万张本地图片、视频和 RAW 文件。
- 需要中文搜索、标签治理、批量 AI 辅助和本地数据安全。

### 1.3 设计原则

1. **本地优先**：素材库、标签和索引默认保存在本机。
2. **人机协作**：AI 只生成建议，用户确认后才写入正式标签。
3. **任务可控**：长任务显示真实阶段和进度，可取消，可恢复，不静默截断。
4. **结果可解释**：搜索、失败、删除和 AI 降级必须让用户知道发生了什么。
5. **数据安全**：删除、移动、恢复和备份均有明确边界，禁止假装成功。
6. **界面克制**：内容优先，减少无关入口、重复信息和装饰性 UI。

### 1.4 平台支持边界

首发目标为 Windows 10/11 x64 完整功能、Apple Silicon macOS 与 Ubuntu 24.04 x64 知情测试预览。平台能力差异、支持等级、暂不支持项和真机验收门槛统一以 [PLATFORM.md](PLATFORM.md) 为准；本 PRD 不重复维护平台矩阵。平台构建成功不等于该平台已达到预览或正式支持等级。

## 4. 非功能需求

### 4.1 性能

- 3 万素材网格滚动无明显卡顿和白块。
- 普通搜索目标 ≤500ms，内部体感目标 <300ms。
- JPG 320px 缩略图目标 ≤5ms，RW2 320px 目标 ≤100ms。
- 高清 RAW 解码必须异步、限流并放在数据库锁外。
- 数据库锁内禁止网络、解码和大文件 IO。

### 4.2 稳定性

- 迁移必须可重入、可恢复，已发布版本不得回改。
- 崩溃或重启后，遗留 AI 批次不得永久停在 processing。
- 备份恢复必须拒绝与运行中的导入、导出或打标冲突。
- 失败写入不得伪装成功。

### 4.3 安全与隐私

- 本地素材和索引默认不上传。
- 云端 AI 只发送用户明确触发处理的素材预览。
- API Key、token 等凭据进入系统凭据库。
- 路径操作必须防止目录穿越；SQL 必须参数绑定。

### 4.4 可用性

- 1366px 和 1920px 宽度无内容重叠。
- 所有图标按钮有可访问名称或 tooltip。
- 选中、错误、禁用状态不能只依赖颜色。
- 关键操作可用键盘完成。

## 6. 发布验收

发布前必须满足：

1. `scripts/smoke.ps1` 完整通过。
2. 自动化质量门禁全部通过。
3. 使用真实素材完成 [QA_PLAYBOOK.md](QA_PLAYBOOK.md) 中 P0 场景。
4. 超级搜索 relevance、mustNot、位置权重和 hydrate 行为有真实数据证据。
5. 导入、查看器、AI 打标、导出、删除恢复、备份恢复主链路无 P0/P1 未解决缺陷。
6. 当前版本的数据迁移、备份和恢复路径已验证。

## 7. 产品不变量

1. 素材文件不得因 UI 假成功而丢失。
2. AI 不得绕过人工确认直接改写正式标签。
3. 搜索条件只有一个执行计划，不允许列表、总数、全选和诊断各走一套逻辑。
4. 分面 key 是机器协议，展示名不是协议。
5. 任何“删除”和“移动”都必须能解释最终文件和数据库状态。
6. 任何降级结果都必须让用户看见原因，不能静默变成另一条查询或空结果。
7. 用户已保存的搜索计划、标签、评分和回收站状态必须跨重启保持。

默认底栏顺序为「入库｜素材库｜中央 Logo｜打标｜百宝箱」。中央 Logo 固定在窗口正中央，作为助手入口；首次进入助手，无历史时新建对话，有历史时恢复最近对话，始终提供新建入口。独立入库、素材库和打标页面保留，与助手保持现行语义主题、控件和视觉规范，不要求每个页面机械采用同样的三列。

2.0 就支持在设置中增删、显示/隐藏和调整已有功能快捷入口，可把设置固定到底栏；移除按钮不删除功能或数据。Logo 保持中央主入口位置。可选项来自受控内置功能目录，不接受任意 URL/可执行文件。百宝箱在 2.0 可见并进入「尚未开放」说明页；2.5 接入真实插件列表、安装管理和固定快捷入口，固定插件后仍保留百宝箱这个完整入口。槽位数量、溢出形式、键盘顺序等在布局原型中确定，不预先冻结插件 SDK。

| 助手区域 | 已确认行为 |
|---|---|
| 左上角 | 小型工作状态区，展示进行中、已完成、未完成等简要状态；缓慢自动轮播，悬停暂停，可手动滚动；旁边直接显示「设置」 |
| 左栏 | 统一对话历史，按最近使用排序，可搜索、改名、归档和删除；不按分库拆成多个历史列表 |
| 中栏 | 对话、附件、计划及持续更新的任务卡；重要异常另行提示，不为每次进度变化追加聊天消息 |
| 右栏 | 导入工作台与标签审核两个页签，另有「本次结果预览」：交接过来的选择只读展示数量与体积，点按钮才在素材库打开可明确退出的临时结果视图（A3-08：右栏不加载素材行）；也显示任务详情。列表/缩略图/单图三视图属入库页待入库清单，不在右栏重复 |
| 宽度 | 工作台需要时自动加宽，聊天保持可见；空间不足优先收起历史列表，可手动调整宽度 |
| 首次使用 | 可跳过的分步向导：总仓位置、AI 配置、主要操作；未配置 AI 仍可手动导入和管理素材 |

**可对话即用与权限档位（R61）。** AI 配置完成即可直接对话，不需要用户额外打开某个开关；配置缺失时按钮给出具体缺项（未绑定服务、连接已停用或缺密钥），而不是笼统提示「请打开联网开关」。

对话框左下角常驻权限选择器，三档：**仅阅读**（只查不改）、**可执行改动**（默认，改动前出批准卡）、**完全权限**（用户批准后模型可在同一轮直接提交，省一次往返）。档位是会话级，新会话回到默认档，不跨会话记忆宽档。「完全权限」必须在选择时说明：**删除仍会单独确认**。任何档位下，批准、恢复、永久清空与打标开始都只能由用户在界面点击完成，模型不能自行批准。

档位只决定模型能用哪层工具，不决定数据能否外发；两者是独立判定。权威定义见[实现契约 §6.2](../plans/v2/12-implementation-contracts.md#62-agent-会话权限档位a3-10)。

交接过来的素材在右栏只读预览数量，不加载素材行；点按钮到素材库打开可明确退出的临时结果视图，右侧不内嵌缩略图流。搜索结果同样提供「在素材库查看」，打开临时结果视图，不自动建分库或移动文件。在素材库选择后通过「交给助手」明确交接，展示具体附件/集合；后续素材库选择变化不能悄悄改写已经提交的范围。

### 8. 导入、审核与跨页衔接

拖入文件或文件夹先作为附件，不立即入库，也不自动向模型外发。点击附件旁「导入」或明确提出导入要求后，右侧展示检查清单、异常项、目标分库及改名设置，再确认执行。自然语言指定目录仍须取得对应读取授权。无需模型连接，也能靠选择文件、设置和执行按钮走完同一导入流程。

独立入库页与助手工作台是同一领域能力的不同视图。同一任务共享清单、设置、进度和结果；不同任务分开保存。入库页提供「交给助手」，显式带入当前准备内容；不因手动使用而自动塞入最近对话，不重复提交已经开始的导入。批次打标完成后可在助手右侧切图、编辑和批量确认建议，也可「打开打标页面」；两处审核同一批数据。批准整段工作流不等于批准尚未产生的正式标签。

设置可开关应用内悬浮助手；默认小 Logo，允许拖动并吸附边缘，在茶馆页面之间切换仍可使用，不做系统桌面悬浮窗。点击继续最近对话，提供新建；不塞入完整历史和工作台。需审核计划时只显示摘要与「查看并确认」，跳到完整助手页。自定义形象不作为本版交付条件。

### 8. 会话、执行与恢复

新对话从空白开始，每段对话分别保留附件、草稿、计划和工作台上下文。切页/切对话不取消已受理任务，右栏跟随当前对话，不被后台其他任务抢占。归档隐藏常用历史但可恢复；删除对话不删除素材、正式标签或必要操作收据，有未结束任务时先处理任务再删除。

普通工作流先展示整段具体计划，用户确认一次后执行已批准步骤；范围或关键条件改变需要重新审核。长任务默认排队，等待可取消，开始前复检条件。输入框「停止回答」与任务卡「取消任务」分开；取消停止剩余工作并保留已完成效果，显示实际结果，不声称自动撤销。

完整退出或异常退出后，再启动先展示已完成/未完成/待核实摘要，用户点击继续后核实并处理剩余项；恢复会话不自动恢复副作用。终止与状态机约束见 [06](../plans/v2/06-permissions-and-data-safety.md)。窗口关闭前的具体提示样式、全局任务详情入口等采用同一任务投影，在交互原型验收，不新增一份独立任务真相。

### 8. 模型、外发与文件夹授权

服务在设置中配置，输入框旁展示当前服务/模型，可切换已配置且受支持的服务。切换作用于后续助手调用；已批准任务保持原计划服务，打标等用途若采用另一服务必须在计划中展示。连接失败保留工作，提示重试或选择服务，不自动换成本机/云端或其他收费连接；影响任务的服务变化重新审核。

看图默认使用压缩预览，需更高清内容时明确提示；压缩仍是图片外发。展示接收服务、数量、清晰度及所需文字信息范围，批量操作纳入计划确认。外部目录默认仅本次任务读取，可主动记住指定目录，在设置中撤销；记住读取不等于入库、写入或外发许可，更不等于将外部目录纳入素材库。

### 8. 单总仓、旧数据与维护

本方案中「总仓」对应现有设置的「总库」概念；物理管理范围以当前一个已验证总仓为准。素材库只建立和保持总仓内托管素材的追踪关系。外部来源用于读取和复制导入，外部目的地用于复制导出；所有手动、Agent、MCP 入口的已有素材移动都限于总仓内分库之间，不再提供追踪库外位置的移动导出。附件、导入来源记录与授权目录可以指向库外，它们不是库外素材索引。

旧库外记录进入待处理清单，不参与正常素材列表及自动清理。用户选择复制回总仓或解除关联，确认后处理，库外原文件不被删除；待处理期间保留标签、评分等整理信息。复制回仓须保持既有资产身份/关联，不能把普通去重导入当迁移成功。失联总仓与真正库外记录必须区分。**已实现（A2-03，批量处置与离线出口见 A4-06）**：逐项与批量都按项给出独立结果，永不聚合成一个「成功」；批量复制回仓仍逐个由可信文件选择器重新选中原文件，用户取消即跳过该项并如实报告；相同完整 SHA-256 的不同记录只展示候选并保留为独立记录，2.0 首版不合并。

2.0 设置提供总仓迁移/重新定位向导：前者由软件搬迁，后者核实用户已经移动的完整总仓，检查通过后切换，不允许直接保存路径造成半迁移。维护不开放给 Agent。总仓临时失联时保留记录和已有缓存，暂停依赖原文件的操作及清理，不自动解除关联。首版范围遵循现行平台契约，支持同一平台内搬迁，不据此承诺跨操作系统搬库。**已实现（A4-05 引擎、A4-06 向导）**：向导先展示任务影响（当前代次未结束的操作、待处理打标批次、入库/回填/导出标志），有未结束任务时不允许开始且由用户自行结束——本应用不会静默取消它们；成功、部分失败、中止与「已切换待收尾」各有明确下一步，关闭窗口或重启后恢复上次迁移摘要而不是新建一次。

### 8. 删除与独立清空

Agent 可以准备移入素材回收站和库内移动计划，经确认后执行。任意资产的直接永久删除仍由可信手动入口提供；Agent 另有独立「清空回收站」能力，不借通用永久删除工具实现。清空单独展示精确清单、数量、空间及不可恢复说明，以「永久清空这 N 项」按钮明确确认，不要求再输入短语；普通整理计划批准不包含清空。

回收站默认保留 30 天，删除计划和回收站显示预计永久清理时间。Agent 清空和到期清理仅处理明确属于当前总仓的托管文件；库外或归属不明项保留并提示手动检查。确认后新进入回收站的条目不加入原清空计划；实际未清理项不能被隐藏成全部成功。工程强制机制见 [06](../plans/v2/06-permissions-and-data-safety.md)。

### 8. 个人常用流程（Skill）

2.0 除内置流程外，支持把成功的素材流程保存为个人常用流程，命名、编辑分库/打标要求等参数并再次调用。建议 UI 落点为任务结果中的「保存为常用流程」及输入框附近的调用菜单；这两个具体控件位置属于交互原型建议，不冒充用户已经逐项确认的像素设计。

保存的是步骤与参数模板，执行时重新绑定本次素材和目录、形成计划、取得批准，不固化上次照片集合或沿用上次权限。不开放任意脚本、Pi extension 或第三方代码安装；个人流程不依赖插件系统提前落地。实现与版本语义见 [03](../plans/v2/03-agent-and-mcp.md)。

**已实现（A4-07）**：保存门只接受 `STEP_CATALOG` 里的七个提交类业务动作与七种参数键，脚本、任意命令与凭据在类型层就无法表达；编辑产生新版本、改名只改名称、停用保留历史版本，在途实例引用的版本号永远解析到原版本。管理入口在助手页与任务结果（「保存为常用流程」），保存前明确列出会用到的能力与复用时仍需现场选择的输入；无法合法表达的历史操作会逐条说明原因并排除，不会改写成脚本。

**已实现（A4-08）**：调用时在 `WorkflowRunDialog` 填写本次输入，点「准备计划」那一刻才快照当前选中素材，服务端重新解析素材集合、导出目录授权与目标分库，生成一份全新计划（`workflows.submit` + Ordinary 审批）——同一条流程连调两次必得两份独立计划，旧批准、旧收据与旧素材句柄结构上无法复用。撤销目录授权后重新使用会直接在准备阶段报 `GRANT_REVOKED` 并指向重新授权入口；流程版本被编辑后旧计划返回 `PlanChanged`。计划里含 `imports.submit`/`tagging.submit`/`trash.empty.submit` 步骤时，这些步骤**永不执行**，只被记成「已跳过」并点名去入库页/打标界面/回收站界面单独确认——流程计划的批准不等于它们的批准，永久清空仍走「永久清空这 N 项」的专属确认。点「确认并开始」后界面**立刻**进入运行视图并逐步骤显示进度，**运行期间就能取消**（取消只停止尚未开始的步骤，已完成的文件效果不回滚），不需要等整次执行结束；运行中关闭窗口不会中断任务，重新打开同一份计划即可读到真实结果，且不会重复执行或重复计费式地新建任务。任何一步没有完全成功时，**依赖它的后续步骤整步不执行**并说明「前置步骤没有全部完成」，而**没有依赖的步骤照常执行**——不会因为前一步失败就把整条流程或无关步骤一起判死，也不会在依赖未满足时按子集偷偷缩小执行范围。与外部客户端的互操作（MCP）属 A5。

2.5 插件中心展示来源、版本、运行模式、权限、工作区占用、连接、启停与更新；增加运行容器及固定入口的贡献点。确认 UI 始终由可信主界面绘制，不允许插件覆盖。

两阶段交付范围和退出条件统一见 [08](../plans/v2/08-migration-and-delivery.md)。2.0 的“接口预留”指有实际消费者的业务 Interface 与明确接入位置，不表示实现 PluginHost、SDK、容器、媒体引擎或空安装表。

**已实现（A5-01）**：本机外部 MCP 接入是**两段链路**：外部客户端经 stdio 连接 `packages/mcp-bridge` 桥接进程，桥接进程再经 Windows 命名管道连到茶馆宿主。桥接进程没有数据库连接、没有文件写执行权、没有网络访问，它只做协议翻译；**写库的永远是茶馆宿主自己**。宿主未运行时桥接给出明确的启动提示并返回空工具表，不会静默另起一个写库宿主。

配对由设置页「数据与隐私 → 本机外部接入」管理，可撤销。默认只勾查询类（`assets.search` + `operations.get`），写类能力必须用户显式勾选；`plans.approve`、`operations.resume` 与 `trash.empty.*` **永不出现在对外工具表**，外部调用 `assets.trash.submit` 永远返回 `APPROVAL_REQUIRED`（本协议没有批准帧，永久删除另有「永久清空这 N 项」专属确认）。客户端自报的名称与版本只作标签，**不参与授权**；身份来自配对记录，令牌由宿主每次启动重新生成的密钥派生、只存在内存与仅当前用户可读的端点文件里。撤销下一次调用立即生效，已入队的写任务不回滚不重放。默认关闭，关闭即删端点文件并断开全部会话。

**已实现（A5-02）**：外部客户端能做的写入只到「准备一份可审查的计划」为止。计划卡直接显示**发起方**——外部客户端的名字取自设置页的配对名称，改配对的名称后立刻同步；配对被删除则显示「已不在配对列表中」，不会留一个过期名字。审核者面对一张计划能同时看到作用范围、预算上限与是谁在申请，不需要凭计划引用猜。

可信完整界面既能**确认**也能**拒绝**：拒绝复用既有的「此计划不再有效」状态，不产生任何执行记录，也不改写素材；被拒绝或已过期的计划再提交会得到明确的 `PLAN_CHANGED`/`PLAN_EXPIRED`，不会静默变成执行。**已批准的计划不能被撤回成拒绝**——撤销已批准的执行要走取消任务，避免撤回批准与在途提交赛跑。

**在哪里看这些计划**：助手页头部的「待审计划」按钮和设置页 MCP 面板里的「查看待审计划」按钮都会打开同一个待审列表。它不挂在任何对话里，因为外部客户端的计划本来就不属于某个对话；列表每次打开都重新向后端读一次，你确认或拒绝之后也立刻重读，所以不会出现「界面上还在等、实际早已过期」的错觉。列表里每一项都写明发起方、范围与预算上限；过期项显示「计划已过期」且按钮不可点。**永久清空回收站的计划在这里只显示、不给确认按钮**——清空有自己的一次性确认流程，在删除对话框里完成，通用列表不会代你批准它。

外部客户端断开不会让它已提交的写入重做：提交带幂等键，重放回同一条任务；任务响应给稳定任务 ID 与查询接口，长任务走普通状态轮询，不要求客户端实现任何实验性 Tasks 扩展。**外部客户端无法准备导入或导出**：目录授权只能由本机可信界面持有（这是「客户端不得与本地会话混淆权限」的实施方式），因此导入/导出/库内移动仍在本机界面完成，外部客户端可查询与准备的是回收站等以素材集合为范围的操作。这条边界是**有意的裁剪而不是待办**：目录句柄与签发它的本机会话绑定，外部客户端没有会话，为它签发的句柄在它那一侧必然解析失败；唯一能绕开的技术路径要求你手工把目录句柄抄进客户端配置，抄错就等于把可读整个目录的权限交给了不在本机界面里的进程。所以 2.0 宁可让它做不到，也不做这个交换（设计依据见 [MCP 桥接契约 §4.1.1](contracts/mcp-bridge-v1.md#411-为什么-20-不发布-imports设计结论不是待办)）。

**已实现（A5-03）**：外部接入的兼容性由**真实的第三方客户端**验证，不是由自造的假客户端。当前已用两套互相独立的官方 SDK 实现（Node 的 `@modelcontextprotocol/sdk` 与 Python 的 `mcp`）跑通初始化、查询、准备计划、拒绝、状态获取、断线重连、任务完成后恢复、宿主关停与重启、撤销配对即时生效、迁仓期间写阻断，以及外部与内置助手、本机界面三种来源**共用同一条写队列**。两套客户端拿到的工具表逐项相同——客户端能力差异只影响体验，不改变业务授权。

**外部写入与内置写入排在同一条队**：三种来源的写任务进同一队列按到达顺序执行，任务结束必须显式释放槽位（不会因为状态变成终态就自动释放）。计划的素材范围在准备那一刻**冻结**：审核期间新入库的素材不会因为「碰巧也在库里」被一起移走，要处理新素材就得重新准备一份新计划。

**连接状态如实呈现**：任务完成后客户端凭稳定任务 ID 重连能读回同一条收据，不会重放写入；宿主崩溃留下的过期端点文件会让客户端明确报「连不上」，不会假装可用；干净关停后工具表为空、写调用明确不可用，重启后同一客户端即可恢复服务。载荷不合规与宿主不可用是两个不同的错误——**前者提示客户端改请求，不会误导用户去重启一个正常的应用**。

HTTP MCP、外部 MCP Broker 和可信原生扩展均为后续独立增量；是否开放以相应 [发布关口](../plans/v2/09-validation-and-risk.md) 为准，不能用任意程序执行入口代替。协议细节见 [`docs/contracts/mcp-bridge-v1.md`](contracts/mcp-bridge-v1.md)（§10 记录了 A5-03 的客户端/平台/版本/场景证据与未验证项）。
