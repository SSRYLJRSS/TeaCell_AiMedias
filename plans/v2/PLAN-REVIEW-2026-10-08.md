## 三、发现的问题（按严重程度分级）

### P1-1 ｜ Pi 基线已过时：v1.1.0 在规划书调研截止后数小时发布【开发前必须处理】

**定位**：`03-agent-and-mcp.md` 第 19–21 行（锁定 `v1.0.4`）、第 360 行（"核实日期为 2026-10-07"）。

**事实**：Pi v1.1.0 于 2026-10-07T22:26Z 发布，npm `latest` 标签当前已指向 1.1.0。规划书全部源码链接锚定 `v1.0.4` tag（链接本身稳定，不会失效），但行为声明以 v1.0.4 为准。v1.1.0 中至少两处变化与本规划直接相关：

1. `agent_settled` 事件新增 `aborted` 字段 → A 卡中事件类型封装若按 v1.0.4 类型生成，遇到新版运行时会缺字段。
2. standalone binaries 修复了 `.env` 加载行为（从启动目录加载）→ 直接影响 03 第 61 行声明"Node 环境不继承无关 provider key、代理和插件配置"的成立条件。**该安全边界声明需要在 v1.1.0 下重新核实**（标记为推测：修复的具体方向以 Pi v1.1.0 release notes 原文为准）。

**风险**：执行 AI 按"装最新版"的直觉执行时，全部行号引用、事件声明、安全边界声明产生静默漂移——这是最典型的"文档没错但基线过期"事故。

**修改建议（二选一）**：
- 方案 A（成本低）：在 03 第 21 行后加硬约束——"实施一律锁 `@earendil-works/pi-coding-agent@1.0.4` 精确版本；升级需重跑 P01 并全文重核行号引用"。
- 方案 B（成本高但更稳）：以 v1.1.0 重跑全部源码级声明核查（约 9 处），更新行号与 `.env` 安全声明后升基线。

### P1-2 ｜ 评估集建设没有任务卡落点【开发前必须处理】

**定位**：`09-validation-and-risk.md` 第 86–88 行声明"从 A0 开始使用可控模型替身验证政策，A4 扩充到约 30–50 条代表性任务"。

**事实**：通读 `execution/A0.md` 全部 7 张卡（A0-01~A0-07），无任何一张卡的"实施步骤"包含"创建初始评估集/政策替身集"。唯一沾边的是 A0 某卡步骤 2 的"跑模拟流式事件"——那是进程生命周期验证，不是评估集。

**风险**：09 的验证策略悬空。A4 扩到 30–50 条的前提是"A0 已有初始集"；若 A0 阶段没人建，A4 只能边补边评，验证结果失去纵向可比性，09 §5 整节失效。

**修改建议**：在 A0 增补一步（落到现有某张 A0-x 卡的步骤里，或新增半张卡），明确：初始评估集条数（建议 ≥5）、存放位置、每条字段（初始库/选择/授权、用户话语、允许结果、禁止副作用、必要确认点——09 已定义好字段，只需指定 owner）。

### P2-3 ｜ sidecar 包体无数值红线，只有"测量后冻结"【建议补强】

**定位**：`09-validation-and-risk.md` 第 119 行："P01/P02 后再冻结具体新增阈值。不能在没有测量时承诺 sidecar 包体、CPU 上限……"

**评价**：方法论上合理（不拍脑袋许诺数字），但缺"超限熔断"触发器。实测数据：`@earendil-works/pi-coding-agent` unpacked 约 22.9MB（npm 实测），加 Node 运行时后 sidecar 总量在 80–110MB 量级，安装包体积将从当前基线成倍增长。

**修改建议**：在 09 第 119 行补一句触发器，例如"P01 实测后若 sidecar 总量超过 X MB 或安装包增量超过 Y%，触发复核并回写本节"。X/Y 可以先留空，由 P01 填——但"超了怎么办"的流程现在就要有。

### P2-4 ｜ Tauri child WebView `unstable` 无上游变更回退策略【建议补强】

**定位**：`05-plugin-platform.md` / `06-permissions-and-data-safety.md` 均依赖 Tauri 2.11.5 的 child WebView（`unstable` feature，已核实属实）。

**风险**：unstable API 在补丁版本间可破坏。若 Tauri 升级时该 API 签名变化，B 阶段（2.5 插件系统）全部 UI 容器代码受冲击。规划书没有写明此情况下的降级出口（如退回 iframe 方案、或锁定 Tauri 补丁版本）。

**修改建议**：在 05 的风险节或 B0-01 卡的"停止并交接"条件中补一条："child WebView API 与 2.11.5 行为不一致时，停止并交接，候选降级方案为 iframe + postMessage"。

### P3-5 ｜ 02 架构图与文字说明互相矛盾【低】

**定位**：`02-target-architecture.md` 第 14 行 mermaid 图直接画 `Chat[聊天页面] <--> Host[完整 Pi SDK Host / Node sidecar]`；第 30 行文字却声明"实际主界面仍经 src/api 与 Tauri 通信，不私建绕过 Rust 的控制通道"。

**评价**：文字澄清存在（说明画图者意识到了），但图本身按"直连"画，与正文相反。执行 AI 只读图不读注时，可能真的私建控制通道——这恰是文档自己最担心的反模式。

**修改建议**：把 mermaid 图改成 `Chat --> Rust[Tauri Rust 核心] --> Host`，让图与文字同向。

### P3-6 ｜ R57 映射表粒度粗，2.0 验收时易被误读【低】

**定位**：`13-requirements-traceability.md` 第 72 行：R57 映射到 A6-02、A6-03、B0-01、B3-03。第 8 行已自我解释"R57 包含 2.0 既有媒体回归与 2.5 可选专业媒体能力"。

**评价**：不算错误（文档有解释），但映射表本身不标注哪几项是 2.5 兜底。2.0 阶段验收时扫表会误以为 R57 已全部有 2.0 侧落点。

**修改建议**：第 72 行映射列加标注，如 `B0-01（2.5 兜底）`。

### P3-7 ｜ A1-01 必读中"error.rs（若重命名先定位）"属多余防御【低】

**定位**：`execution/A1.md` 第 12 行。

**事实**：`src-tauri/src/error.rs` 现网存在（已核实）。括注是噪音，无害但增加执行者的困惑面（会疑惑"是不是预期它会被重命名"）。

**修改建议**：删掉括注。

### P3-8 ｜ sidecar 进程生命周期验收场景不全【分析项，供参考】

**定位**：`execution/A0.md` 第 34 行已覆盖启动失败、异常退出、stdout 污染、超时、只回收自己创建的进程（这是好的）。

**缺口**（未在任何 A0 卡看到明文）：崩溃后是否拉起（watchdog 策略）、应用退出时 sidecar 回收的时序保证、Windows 下僵尸进程防护、双开应用时 sidecar 单实例冲突。这些不必现在就设计，但建议 A0-01 的验收场景补两条负向用例，把"没考虑"变成"考虑过并决定不做"。

### P3-9 ｜ Clash 代理环境对 sidecar 出站的干扰未列入验证矩阵【分析项，供参考】

**背景**：本机 Windows + Clash 系统代理环境，曾出现 heif-bin 大文件上传被代理截断的故障。

**风险**：sidecar 的 provider 出站 fetch 是否继承系统代理、继承后是否复现截断类问题，规划书未提。03 第 61 行有 env 隔离声明，但 P01 的"真实支持模型"验证若只在无代理环境跑，上线即踩坑。

**修改建议**：在 P01 验收中加"代理开/关对照"一条，成本极低。

### P3-10 ｜ Pi 版本升级流程无 owner【分析项，供参考】

**定位**：R01–R60 全部约束 + 14 份文档，无任何一条负责"Pi SDK 后续版本升级评估"。

**建议**：在 `14-review-and-handoff.md` 的交接清单中加一条"升级检查清单"（重跑 P01、核对行号引用、核对安全边界声明、评估 agent_settled 等事件 schema 变更）。

## 四、值得保留的优点（执行时不要因为本报告而砍掉）

1. **源码级引用锚定 tag**（`blob/v1.0.4/...`）：链接不会随 main 漂移，这是多数规划书做不到的细节。
2. **"第二个 AI 的认可仍不是证明"**（10 号文档）：对 AI 复核边界的认知清醒。
3. **每张卡的"停止并交接"机制**：把失败模式显式化，远好于"尽力而为"。
4. **09 第 119 行"不能在没有测量时承诺"**：反拍脑袋纪律，与问题 P2-3 不冲突——缺的是熔断触发器，不是数字本身。
5. **R57 的 2.0/2.5 拆分声明**（13 号文档第 8 行）："不能把可选项当 2.0 阻塞"，范围控制得当。
