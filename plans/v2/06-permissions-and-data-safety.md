# 06 权限、写入约束与数据安全

状态：跨版本推荐契约，尚未实现。本文拥有跨 Agent、MCP、插件的通用授权和操作语义；2.0 落实 Agent/MCP 与既有业务所需部分，插件主体、工作区和新增媒体部分在 2.5 实现，不提前创建空授权或安装表。分期见 [08](08-migration-and-delivery.md)，插件运行见 [05](05-plugin-platform.md)，媒体产物登记见 [07](07-media-workflows.md)。

## 1. 安全目标和承诺边界

目标是让模型错误、提示注入、普通网页插件恶意调用、重复请求和进程崩溃不能绕过业务范围或造成假成功。模型、素材内容、网页、工具返回值和插件脚本均不具备授予自己权限的资格。

可信计算基础包括 Rust 宿主、应用随包的 Pi Host 代码、明确批准的原生连接器、OS/WebView 和所用原生库。独立 Node 进程主要隔离生命周期，不保证隔离恶意原生代码；Node 官方明确其 Permission Model 不能作为恶意代码安全边界。该限制同样适用于试图用进程工作目录、环境变量或 JS 包装器构造的“沙箱”。[Node 官方权限说明](https://nodejs.org/api/permissions.html)

普通插件通过受控宿主能力访问文件和网络。可信原生扩展另行安装、明确告知同账户系统权限，默认不被 Agent 自动调用；不能声称其所有直接 fs/net 行为可由茶馆撤权拦截。若将来要求运行不可信原生程序，必须新增经过目标平台验证的 OS 级隔离，不以 manifest 声明代替。

## 2. 可信调用上下文

由通信 Adapter 生成 CallerContext，而不是接收调用方提供的同名字段：

| 字段 | 用途 |
|---|---|
| principalId/type | 区分主界面用户、内置 Agent、插件、外部 MCP 客户端 |
| sessionId/instanceId | 当前对话、WebView 或已认证连接实例 |
| originChain | 用户 → Agent → 插件/外部工具的委托关系 |
| grantEpoch | 权限撤销或修改后的版本，旧资源句柄失效 |
| libraryId/libraryEpoch | 当前库身份及恢复/重建世代，防止旧 ID 指向新库 |
| requestId | 关联请求、诊断和幂等处理；不是认证凭据 |

WebView 身份取自宿主真实调用对象与实例映射；MCP 身份取自配对/认证，不取 clientInfo.name；Pi 身份取自宿主启动与握手。连接重新建立必须重新绑定实例，不沿用未验证的旧消息身份。

有效权限取应用政策、安装包允许能力、用户授权和本次委托范围的交集。Agent 调用插件不能获得二者权限的并集。插件需要上传素材时，读取与外发都要满足授权。可信原生代码的 OS 直接行为不属于该交集机制可以强制覆盖的范围。

### 2.1 外部 MCP 的本地配对提案

stdio bridge 是协议适配器，不能因为由某个客户端启动就自动取得全库权限。建议首次使用通过以下流程建立独立客户端主体：

1. 用户在茶馆可信设置页启用本地接入，创建具名连接，选择可用能力、库/集合和有效期；默认从只读开始。显示的客户端名称仅作标签。
2. 宿主生成短期、单次配对凭据。bridge 与现有宿主建立受当前用户限制的 named pipe/Unix socket 连接，完成配对后换取该连接专属的随机凭据；不在命令行参数、普通日志或公开配置中放长期秘密。
3. 长期凭据保存到受支持的系统凭据存储；外部客户端配置只保存连接标识。后续握手核对凭据、协议版本和授权状态，宿主绑定会话主体。连接凭据只授予已批准能力，不授予未来新增工具。
4. 写操作仍走具体计划与可信 GUI 确认。用户在茶馆可查看连接的范围、最近使用和活动任务，单独撤销；撤销提升 grantEpoch，并让已有连接下一次调用与下一步副作用检查失效。
5. 端点访问控制、配对、凭据不可用及重连需要三平台 PoC；不能以 socket 路径保密或 clientInfo.name 作为认证。维护状态、宿主关闭、凭据丢失时失败关闭，不另开数据库。

该流程区分正常客户端的授权与审计，不证明能够抵御同账户恶意本地程序冒用凭据存储或注入进程。更强的应用身份绑定、远程 HTTP 认证和委托审批均需独立设计，不随 stdio 接入隐含开放。

## 3. 权限类别与低摩擦授权

权限应围绕实际操作，不提供一个笼统的“完全访问素材库”开关作为默认方案。以下 ID 为提案，冻结时由契约生成各入口类型。

| 能力 | 默认处理 | 约束 |
|---|---|---|
| assets.query / preview.read | 已授权范围内可直接执行 | 限定库/集合、分页、返回量；原图读取另授权 |
| workspace.read/write | 插件自身空间可持续使用 | 配额、路径校验、版本/实例映射；不得逃逸到主库 |
| directory.read / export.write | 用户选择目录并授予范围后使用 | 区分读写、递归、期限；不等于全盘 |
| assets.import | 预览并批准具体计划后执行 | 来源、数量、目标、托管/改名规则 |
| assets.move / assets.trash | 批准具体素材集合与影响后执行 | 已验证托管素材，移动目标限当前总仓内；移入回收站不等于永久删除 |
| trash.empty | 独立固定清单及可信 GUI 清空确认 | 仅已在回收站、托管归属明确的项；不接受任意路径，不继承普通整理批准 |
| tagging.suggest | 批准范围及模型/外发后启动 | 生成 pending 建议；不自动成为正式标签 |
| labels.confirm / destructive.write | 可信主界面明确确认具体变化 | Agent/插件不能自行制造确认；Agent 不获任意单项永久删除能力，清空走单独受限能力 |
| network.connection.use | 批准连接、用途和外发类型 | 不开放任意代理和凭据读取 |
| connector.invoke | 批准连接器/动作/参数范围 | 禁止通用 command string；费用与资源上限 |
| application.admin | 首版保留给可信设置 UI | 凭据导出、数据库迁移/恢复、重置不向通用 Agent 工具开放 |

授权可选择“本次任务”或“在撤销前允许该插件使用所选目录/连接”，不要求每个读取和每一张图片反复弹窗。会造成素材正式变化的任务仍使用具体计划；一个明确工作流可以整体批准其中的导入和生成建议步骤。正式标签确认和危险操作遵守当前 PRD，不在此静默变更。

## 4. 操作计划与批准协议

Plan 至少包含 planId、能力契约版本、执行主体/委托链、libraryEpoch、输入集合及摘要、目标、关键配置摘要、预期影响、费用/数量上限、有效条件与 planHash。后端保存精确范围，不把一段自然语言当可执行批准对象。

1. prepare 只读取/预检查并产生后端计划，必要的临时预览要有配额。
2. 主界面根据后端计划展示确认卡片；不能使用模型任意 HTML 绘制系统批准界面。
3. 用户明确批准后，宿主建立 approval，绑定计划 hash、主体、范围、期限和限制。
4. submit 校验身份、当前权限、计划未过期、库未替换、配置和输入仍满足条件，再原子登记操作与批准消费。
5. 关键范围变化返回 PLAN_STALE/REVIEW_REQUIRED，不能自动套用旧批准。

approval 不能由工具参数 approved:true 或聊天摘要创建。外部客户端的确认提示不是茶馆批准记录，除非将来有专门且经过认证的委托审批协议。首次提交缺少批准时返回 approval_required 和 planId，再由茶馆可信界面完成审核；此时尚无 operationId。计划的 reviewStatus 与已受理操作的执行状态分开，批准后 submit 才原子消费批准并创建 operation。

AI 打标批准只授权固定的素材/成功收据集合、连接与模型、外发策略、分类提示快照和请求上限。批准后的 submit 仅原子创建待启动批次与 operation 子任务绑定，不发送网络请求；只有可信 GUI 对该 operation/step 的显式启动动作可以外发。重试同一导入 operation/step 必须取回同一批次；改变重复映射纳入选择必须冲突并重新准备。启动前复核来源收据和配置仍有效；运行时每次网络发送前持久消耗请求预算，429、取消或崩溃后保留已生成建议及预算消耗，不自动重发结果不明请求。API 密钥不得进入计划/批次快照，运行时只从宿主凭据服务解析。

用户已经批准的正常低风险步骤不应重复询问；越界变化必须重新形成计划。批准等待期间不持有数据库锁、资源独占锁或阻塞工具线程。

## 5. 幂等与冲突

提交幂等键由业务提交边界生成并持久化；同一个工具调用重发使用同一键。建议唯一范围为 principal + libraryEpoch + capability + idempotencyKey。相同键相同计划返回原 operationId；相同键不同参数返回冲突。不能只使用每次新生成的模型 toolCallId 来保证跨重试幂等。

批准的消费与 operation 创建在同一个短事务中。进程在提交后、回复前崩溃，重试仍返回同一任务。相同计划被多个调用者消费不能扩大权限。

operation 受理幂等还不够：向既有 AI batch/export task 派发时，以 `(operationId, stepId)` 固定执行身份。创建本地子任务与保存关联应在同一数据库短事务完成，或由子任务服务接受持久唯一创建键并可查询结果。恢复 worker 先取得已有子任务，不再次 create_batch/create_task。操作层持有编排状态，域任务服务持有该步骤的实际执行状态；前者从后者推导结果，不双写另一份独立批次进度。外部请求若无幂等支持或可核实结果，不以本地 processed 计数推定未提交；不确定项仍按 outcome_unknown 处理。

2.0 长业务任务默认排队，所有入口共享同一任务受理和冲突检查。等待新标签审核、清空批准等人工输入时释放执行资源，不持有 DB 锁或把整个队列阻塞到无人操作；是否可执行下一步取决于依赖和当前批准。草稿与待审计划不冒充已排队 operation，前端「等待确认」与「等待执行」分别展示。

对同一资产的移动/删除/显影使用资源冲突策略和 revision/输入指纹；读取可并发，冲突写入失败或排队。排队后执行前再次检查权限和条件。既有 import_running 等互斥语义先保留，不在首批改造中盲目放开并行。

显影与上传使用固定输入 snapshot，复制完成后核实完整摘要并绑定批准计划；源文件在长复制中变化不能导致处理内容与来源记录不符。快照准备、封存和计划失效规则见 [07](07-media-workflows.md)，禁止仅凭路径、asset ID 或 mtime 放行。

## 6. 状态与恢复

操作主状态：queued、running、succeeded、partially_succeeded、failed、cancelled、interrupted、outcome_unknown。首次执行前的待审属于计划，不提前创建执行任务。已受理的多步操作若等待产物选择或新增批准，记录等待阶段/原因并停止对应步骤，不能因已有 operationId 绕过审批。取消中的请求另有 cancelRequested 与阶段，不能收到 cancel ACK 就宣布已停止。

| 状况 | 必须呈现的事实 |
|---|---|
| 部分文件成功，其余失败 | 保留逐项结果，计数一致，不显示全成功 |
| 用户停止模型回答 | Pi 推理停止；已提交业务任务按其授权继续，明确可单独取消 |
| 云端请求超时但可能已接受 | outcome_unknown；查 provider job ID/请求记录，不能盲目付费重试 |
| 本地进程异常退出 | interrupted；检查输出和 DB 收据后判断可续跑项 |
| 文件已落盘、数据库登记失败 | 暂存/目标位置有恢复记录，按 artifact/receipt 核实；不再次生成 |
| 已撤销权限 | 拒绝新调用和后续可停止的副作用，报告已执行部分 |

不能承诺跨 SQLite、文件系统和远程服务的 exactly-once 事务。SQLite 事务只覆盖其管理的数据提交；文件/网络需操作日志、确定目标、幂等登记和恢复核实。不要把文件 IO 放进长数据库事务来营造原子性。[SQLite 原子提交范围](https://sqlite.org/atomiccommit.html)

逐项状态用于事实，通知用于交互。进度事件带操作和序列号；客户端断线后重新拉取快照。业务错误码区分授权、计划失效、资源冲突、服务失败、状态未知和环境缺失，不能全部转成“模型出错”。

自动恢复快照与继续执行分开：应用重开可以自动对账和展示摘要，不自动推进未完成的副作用；用户点击继续仍需检查当前批准、授权、输入和库身份。取消操作不反向删除已成功导入的项、不自动把移动回滚；回滚/补偿必须依据收据另行准备。模型流停止也不取消已经被宿主受理的业务任务。

## 7. 路径、工作区和资源句柄

DirectoryHandle/AssetHandle/ArtifactHandle 绑定主体、实例或持久 job 授权、资源、用途、有效期、grantEpoch 和 libraryEpoch。不能凭 asset ID 或拿到 URI 就获得读取资格。

- 授权目录由可信选择器或配对流程确定；处理 Windows junction、符号链接、大小写和跨卷路径。
- 执行前验证真实目标；有条件时使用 OS 文件句柄及不跟随链接的打开策略，不能只比较字符串前缀。
- 插件文件 API 不返回主库路径，不允许访问应用凭据和其他插件目录。
- 写入工作区先暂存，完整校验再替换；最终输出 create-new/冲突避让，避免默认覆盖。
- 大文件使用宿主管理的流/句柄，限制长度和并发；不通过聊天或普通 JSON 传无限 base64。
- 当前应用级 asset protocol 放行不等于插件授权。插件资源网关校验每次读取，且 CSP 不允许绕过它读取通用 asset URL。
- 安装包解压限制规范路径、链接、总大小、文件数与压缩比，拒绝越界写入。

### 7.1 托管资产与破坏性操作

产品范围以 [02](02-target-architecture.md) 的单总仓和删除规则为准。工程上需要可核验的 libraryId/root 定位、资产相对位置或等效受控映射、文件身份/摘要及托管来源证据；仅有旧 `file_path` 字符串、目录前缀或模型返回路径不构成文件所有权。绝对路径迁移到哪种字段布局在 A1 冻结，已有迁移不修改。

- 普通素材查询排除旧库外待处理记录；临时附件/目录读取授权/导入来源收据与素材索引分域。源文件位于库外不妨碍授权导入，但入库成功的 asset 必须指向总仓托管副本。
- 库内移动验证来源与目标均属于同一库身份，检查链接/真实路径及输入指纹；以不可覆盖的创建/提交方式落实同名避让，不能只依赖提前 exists 检查。文件效果与路径更新均留收据，半移动不得报成功或靠重导入掩盖。
- 复制导出不得删除源文件或把 asset 路径改成外部目的地。旧 move-export 入口、原始 Tauri command、MCP 等都受同一规则，隐藏一个前端选项不算完成。
- 清空计划由宿主查询当时已软删且归属明确的集合，记录删除状态版本、库世代、文件身份和计数。恢复出回收站、文件替换、位置变化或撤权使对应批准失效；新软删项不加入原集合。Agent 不能先软删后借一次普通计划批准自动清空。
- 定时清理使用独立的宿主维护身份，仅处理保留期限已到且仍符合托管/软删条件的项；不能给 Agent 一个能伪造「到期」或「维护调用」的参数。离线、库外、归属不明项跳过并可查原因。
- 磁盘删除失败保留记录；文件已删除但 DB 更新失败使用持久收据完成修复，不把未知文件重删一次。永久删除结果必须逐项可核对，不能用普通事务宣称文件可以回滚。

### 7.2 旧数据整理、迁仓与重新定位

这是可信手动维护能力，不注册通用 Agent/MCP 工具。建议按以下顺序实施，实际恢复点须在 A0/A2 验证：

1. 备份并预检，区分当前总仓失联、路径已变化、真实库外记录和归属不明。进入维护门，阻止冲突任务；启动旧数据分类与保护必须早于到期清理。
2. 对旧库外待处理项，复制回仓以专门的迁移身份保留 asset ID、标签、评分和关联。遇到哈希重复不能直接返回普通导入的 duplicate 并丢掉旧元数据；需明确冲突/合并预览，未经确认保留待处理。解除关联清理的是库管理关系，不能删除库外文件；待处理资料与可恢复清单在确认/事务完成前保留。
3. 软件搬仓先预检目标空间、目录权限、重叠路径、大小写/同名冲突及资产清单，采用带校验和恢复记录的复制/切换阶段；不能先删除旧文件再证明新位置完整。未追踪的目录内容不能因位于旧总仓就自动删除或迁移为资产，列为需处理内容。
4. 用户已手动搬仓时，重新定位验证库身份和文件清单，不能仅凭同名目录信任新路径，也不把失联库当作要解除关联的旧库外数据。明确跨操作系统搬库不在现行平台承诺内。
5. 文件验证与 IO 在 DB 锁外；完成后以可恢复的短事务切换库定位和相关索引映射，刷新不可复用的库世代、失效旧路径计划/句柄。权限不能随新路径扩大范围，记住的来源目录授权重新核对。
6. 任一阶段中断均有可核实恢复点，源端清理是显式、受范围约束的维护阶段。新仓未经确认和核验不能宣告迁移成功，清理失败显示残留，不默默销毁旧数据。数据库、会话、缓存不一定存放在素材根中，不能把搬素材目录等同于搬完全部应用数据。

迁仓/旧记录处置的精确状态字段、源端清理时机与冲突 UI 属于工程方案/原型验收项；不在未经验证前承诺跨文件系统原子搬迁。
A2-03 的处置状态、完整哈希冲突预览、独立保留规则和可恢复收据以[实施契约 §4.1](12-implementation-contracts.md#41-总仓与待处理记录)为准。

## 8. 网络、凭据与预算

读取、联网和外发三种授权分别表达。持有图片读取权限不意味着允许向任意服务上传。普通插件只传 connectionRef 和受控请求参数；密钥注入由后端完成，禁止返回 Authorization、keyring 内容或完整敏感响应头。

网络请求验证 scheme/host/port、DNS 解析和每次重定向；默认拒绝任意 loopback/内网代理。用户配置的 ComfyUI/Ollama 本地连接可以单独授权精确地址。不得自动将茶馆客户端 token 转发给第三方服务。

宿主代理和浏览器 CSP 同时约束请求；包括图片/字体/脚本/表单/WebSocket 等通道。包更新不能借远程 JS 绕过版本审查。连接额度在 Agent、搜索、打标、插件和实际重试间共享。

预算包括步骤数、执行时长、并发、产物大小、模型请求数及用户设置的费用上限。无法准确取得服务计费时只报告估算，不显示伪精确金额。触顶进入可解释的等待/终止状态，不能让模型无限规划或反复重试。

## 9. 恢复备份、升级与多入口维护

维护开始先阻止新操作和 MCP/插件提交，等待或安全取消受影响任务，暂停 Pi sidecar，取得现有数据库维护锁后备份/恢复。恢复完成更新 libraryEpoch，废弃旧计划、集合、资源句柄和待批准任务。外部客户端收到明确维护/库已变更错误。

libraryEpoch 必须是本次恢复新生成且不可复用的世代标识，例如高熵随机 nonce；不能从备份内的旧计数简单递增，否则重复恢复同一备份会重复世代。授权撤销状态属于宿主安全域，不随素材库回滚；恢复不得复活本机已撤销的 grant、配对凭据、待消费批准或 native 信任。若无法安全合并当前授权记录，选择失效后重新授权。新世代及失效处理完成前不重新开放任何业务入口。

任务、产物映射、配方和会话索引纳入一致性备份设计；Pi JSONL 和插件工程单独建立清单/版本，不能假定 SQLite 备份已覆盖。恢复到其他机器不得自动恢复原生扩展信任、客户端 token 或外发授权。

旧应用不能无条件打开升级后的库。提供升级前备份和兼容检查；应用二进制回退与数据回退分别说明。禁止覆盖用户后续已产生的数据来实现“自动降级”。

## 10. 可观测性与提示注入

诊断仅保存 principal 类型/脱敏标识、能力、operationId、阶段、错误、耗时和策略版本。遵守现有日志不保存完整提示词/请求体/素材内容的规则。会话记录、用户批准保存的生图配方属于单独的数据产品，提供保留、清理和导出方式，不自动进入诊断包。

EXIF、文件名、网页文字、第三方工具描述和返回结果都按不可信数据处理；它们不能改系统指令、增加工具、安装扩展或批准自己。工具结果限制长度和结构；远端 HTML/Markdown 在聊天中受控渲染，不执行脚本。权限和计划校验在模型外执行，不依赖模型正确识别每次注入。

验收场景和发布阻断见 [09](09-validation-and-risk.md)。
