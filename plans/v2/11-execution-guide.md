性质：静态执行指导；产品范围见权威 PRD，实际实现状态唯一见 [PROJECT_PLAN](../../docs/PROJECT_PLAN.md#9-20-agent开发状态)。授权、状态判据、依赖解锁、缺口补验与验证有效性统一按 [14](14-review-and-handoff.md#1-一张卡通过的条件) 执行。

首次派工从 A0-01 开始；接续开发先核对当前工作区与证据，从首个未闭合缺口继续。2.0 有44张卡，2.5有11张后续卡；卡数不表示完成比例。

**接续纠偏必读：[PROJECT_PLAN §9.1 当前纠偏计划与接续入口](../../docs/PROJECT_PLAN.md#91-当前纠偏计划与接续入口)。** 当前阻断、修复顺序和复验结果只在那里维护；本指导书、任务索引和14继续定义执行与验收方法，不从先前切片的“已收口”或下游文件存在推断依赖已通过。

现在负责人只需使用下面的派工模板；执行者在首张卡核实基线，再依次完成原型、共享基础、手动链路、Pi/GUI、文件管理与流程、MCP和最终验收。详细顺序由 [任务索引](execution/README.md) 拥有。2.5先重新验证容器，不在2.0实施插件安装器。

## 1. 负责人怎样派任务

1. 第一次从 [A0-01](execution/A0.md#a0-01) 开始，核实基线与文档承接；即使授权完成整个2.0，也按卡执行与验收，先验证地基。
2. 查 [任务索引](execution/README.md)，只派前置任务已经验收的一张卡。遇到标为「需设计复核」的任务，把产物交给能判断架构/数据风险的复核者，再释放依赖任务。
3. 将下面的派工文本交给执行 AI。它只需读当前卡指定的文件；不把全部研究报告一次性塞进上下文。
4. 收到完成报告后，用 [验收与交接规则](14-review-and-handoff.md) 核查实际差异和证据。代码生成完毕不等于任务验收通过。
5. 每次交接更新 `docs/PROJECT_PLAN.md` 的真实状态与缺口；通过后再派依赖卡。本目录任务卡是静态执行要求，不勾选出另一份实际进度。

上述模板用于单卡授权；连续授权的范围与推进规则见14。路径随负责人分配的真实 checkout 调整，不在应用代码硬编码这台机器的路径。

### 连续开发时怎样使用本指导书

连续开发沿用用户授权，按 [14 的状态与依赖规则](14-review-and-handoff.md#状态依赖与授权) 逐卡补齐证据并推进；真实阻塞按第3节分流。

2.0完成以A6-04的逐项交付复核为准。42张卡的文件全部生成、模型回复“任务成功”或自动化测试单独通过，都不能替代实际业务结果、故障恢复、平台支持与真机验收。2.5后续卡不会因连续授权2.0而自动开工。

## 3. 每张任务卡的执行闭环

1. **核实**：记录 checkout、HEAD、`git status --short`、前置任务证据；区分已有改动和本任务改动。读取卡上源码位置，画出本任务实际调用链。
2. **定界**：列本次目标、准许修改的文件、需要新增的文件、可观察输入/输出、失败行为。拟建路径尚不存在是正常情况，但只能在对应任务创建。
3. **先定义验证**：用卡内正常/负向/故障场景准备小型测试数据。数据迁移、业务、安全和进程任务需行为测试；纯可逆样式变化使用视觉/可访问性走查，避免无意义实现镜像测试。
4. **实现一个行为切片**：从既有调用者接入共享 Module，完成依赖的 Rust → API → store/UI 链路。分步提交给复核不等于必须 Git commit；提交和推送仍需用户明确要求。
5. **验证**：先定向测试，再按仓库要求执行相关完整门禁；定向筛选必须实际执行到目标测试，0 tests 不能算通过。完成后只因新修改或新问题重复验证。
6. **自查**：检查差异、权限/数据不变量、错误路径、平台能力、未接通入口、残留旧实现和文档落点。修复卡内问题；越界问题给出阻塞信息。
7. **交接**：按 14 输出结果、命令/退出码/执行测试数、文件、未完成项、复核意见和下一卡候选。按14分别记录各层证据与缺口。

单卡是实现与验收边界，不会缩短用户明确给出的连续开发授权。连续授权期间，验收一张卡后回到 [PROJECT_PLAN](../../docs/PROJECT_PLAN.md) 和 [任务索引](execution/README.md)，只推进所有前置均已通过的下一张卡；某张前置未通过时，先修复或复核该前置，并可继续已放行且互不依赖的工作。遇到缺失的用户决定、权限、凭据或真实设备时，只暂停依赖它的任务，并记录恢复条件；不把等待、代码存在或旧验证当成通过。

### 处理意外的分流

| 发现 | 执行动作 | 可否继续依赖工作 |
|---|---|---|
| 文件改名，但既有职责/契约等价 | 用 `rg` 找真实位置，记录路径映射 | 可在等价范围内继续 |
| 同一卡内部的实现缺陷 | 以失败证据修复，补行为验证 | 可；重跑受影响验证 |
| 前置产物不存在、接口/状态语义未冻结 | 输出缺口、涉及任务、最小候选方案 | 停止依赖部分，等前置/复核 |
| 必须增加工具权限、范围或改变用户行为 | 提交具体变更提案及影响 | 负责人决定前不扩大范围 |
| 同一失败经两次有证据的不同修复仍未解决 | 保留差异、复现命令和两次假设；请求诊断 | 不继续堆补丁或重写无关 Module |
| 原生库/真实模型/目标设备不可用 | 区分环境阻塞和产品失败，提供已完成证据 | 可做独立工作，不能标该门禁通过 |
| 新测试只能通过跳过/放宽契约才通过 | 保留失败并报告冲突 | 不可用降低门禁解锁 |

## 4. 必须由代码和验证守住的约束

这些是执行检查索引，完整规则见原始文档，不在此定义第二份协议。

- 所有领域写入归 Rust；GUI 经 `src/api`，Pi/MCP 经受信任 Adapter；SQL 留在 `db/`，业务留在 `services/`。
- 拟议通用数据从可信调用上下文和宿主记录取得；模型、聊天文本、第三方内容不能制造身份、批准或实际完成状态。
- 状态列表只是读取时的投影；在确认、恢复或文件副作用前重新核验资源当前可用性、身份和版本，不以启动时或列表时缓存的 `ready` 放行操作。资源失联/变化时按唯一领域契约失败关闭并保留可见状态。
- 准备计划、批准、提交、执行收据、恢复相互关联。具体定义见 06；重试不得重复效果或复活过期权限。
- 单总仓管理、托管归属、离线保护、库外旧记录处置与向导见 02/06；所有旧入口一起收敛。操作测试使用临时目录。
- 迁移追加且幂等；锁内无网络/解码/大文件 IO；文件系统与 SQLite 的分阶段失败需要真实收据，不能声称一个事务全部回滚。
- 当前业务测试与搜索/分面契约继续有效；实施已批准的行为变化时定向更新契约和测试，并解释预期差异。
- 平台差异来自统一能力层；当前成功只证明当前环境，目标平台失败不得静默忽略。
- 模板和 Skill 只复用受控业务能力；插件实际运行留在 2.5。既有底栏自定义和百宝箱说明页属于 2.0。

## 5. 复核关口和上下文交接

能力较弱的执行 AI 可完成范围固定、契约已定的代码切片。以下结果必须由能判断对应风险的复核者检查：Pi 模型治理、路径与托管证明、迁移/文件恢复、批准消费与幂等、实际永久清空、MCP 身份、插件隔离。依据见 10；这不能被文档长度或模型自称完成替代。

A0/A1 的复核者可以是负责人或单独安排的审查 AI；本指导书不自行联系其他人。复核不意味着重新询问已经确定的产品选择，重点检查证据是否支持实现。

上下文即将不足时，先用 14 的交接模板记录**已发生的事实**：当前卡、文件差异、已通过/失败命令、未解决点、下一条具体动作。新会话先对照实际文件和 Git 状态核实，不仅靠摘要继续。不要把未来卡的“应该做”混成当前卡的“已经做”。

## 6. 进度与估算

任务索引提供依赖和阶段，不填假日期、百分比或全完成勾选。实际进度唯一写在 `docs/PROJECT_PLAN.md`：当前任务、状态、证据位置、阻塞、下一任务。每卡只有满足验收才完成，不用“编码 90%”代替证据。

A0 的原型结果出来后再估算工时：按剩余卡的变更范围、外部依赖、平台验证和复核成本估算区间。个人效率、模型输出速度都不能替代故障测试/真机验收的实际耗时。2.5 在 B0 重新估算，不以当前草案冻结未来安装格式和 SDK。

本指导书不承诺低能力模型无错误，也不承诺后续绝不重构；目标是把误解限制在小范围内，通过明确输入、共享契约和证据及时发现。

## 7. 接续派工前的逐项检查

这是交付入口检查，不另定义产品需求、接口或实际进度。负责人在派出下一张卡之前逐项核实：

1. **找到真实起点**：先查看PROJECT_PLAN第9节，再核对相关文件与原始验证结果。已有原型可复用其证据；卡内缺口继续补齐，不重做已证明部分，也不直接复制为生产实现。
2. **锁住本次范围**：用任务索引选定卡ID和依赖，用13定位对应需求。2.0任务只包含A卡；B卡保留为2.5储备。较大的卡按任务索引所述拆成行为切片，整卡验收条件保持完整。
3. **补齐工程决定**：逐项查看12第1节中与本卡有关的设计结论。准确接口、权限语义、状态归属、恢复判据缺失时先完成前置设计；将候选名与实际文件映射写进本次任务说明。
4. **给足最小输入**：派工文本提供本卡、前置证据、准许修改范围、所需契约和测试数据位置。执行者开始时列出将观察的真实结果，例如资产数量、文件身份、标签状态、请求次数或进程退出结果。
5. **指定复核者**：数据、权限和生命周期卡明确谁核查失败证据。自查、设计复核、自动化检查和真机验收分别记录，缺一项不能用另一项的成功代替。
6. **确定交付去向**：实际状态只更新PROJECT_PLAN；产品、架构、平台、UI和协议变化回写各自权威文件。临时证据遵守仓库文档生命周期，不新增另一份长期进度表。
7. **关闭当前卡，再释放依赖**：使用14的报告模板，列出已执行与未执行验证、剩余风险和下一候选。A6-04逐项复核通过才表示2.0开发完成；完成规划本身不会自动授权提交、推送或发布。
